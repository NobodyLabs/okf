# Подготовка репозитория под OKF-бандл

Скилл `okf` умеет написать и обновить бандл, но ничего не заставляет его обновлять.
Опыт первого проекта: без механики за ~200 коммитов бандл не обновился в потоке ни разу и
догонял код пачками по 50–66 концептов. Этот скилл ставит механику: принуждение в
момент, когда дифф уже реален (Stop-хук), то же правило для всех коммитов (гейт в CI,
отказ — строкой в коммите), фон (SessionStart), валидность (CI), сеть безопасности
(guardian) и — если бандл нужен кому-то снаружи — MCP для заказчика.

Всё, что ставится, лежит в этом скилле: скрипты и knowledge-mcp — в `assets/`, пример
манифестов для Helm-чарта — в `assets/k8s/`, порядок действий — здесь и в `references/`.
Скилл не знает, где у команды реестр образов, кластер и секреты: это либо решает
пользователь, либо приносит скилл стандарта команды (см. §0).

## Что ставится

| Слой | Где | Как ставится |
|---|---|---|
| Инструменты дрейфа/валидации | `scripts/okf/*.py` | `install.py` |
| Stop-хук + SessionStart-хук | `.claude/settings.json` (merge) | `install.py` |
| Где бандл и правило «правишь код — обнови концепты» | `AGENTS.md` между `<!-- okf:begin -->`/`<!-- okf:end -->`; `CLAUDE.md` подключает его строкой `@AGENTS.md` | `install.py` |
| Механика обслуживания: слои, команды, сигналы дрейфа | `.claude/rules/okf.md` с `paths:` из `resource:` концептов | `install.py` |
| Слияние параллельных веток: `log.md` и якорь — union, дата концепта — драйвер | `.gitattributes` между `# okf:begin`/`# okf:end`; `scripts/okf/merge_driver.py`; `merge.okf.driver` в `.git/config` | `install.py`; в каждом клоне — SessionStart-хук |
| Стражник | `.claude/skills/okf-guardian/SKILL.md` | `install.py` |
| MCP для заказчика | `<mcp-dir>/` (движок + `src/project.ts`) | `install.py --with-mcp` + ручная настройка |
| Гейт долга ветки (`drift.py --gate` на PR и пуше в интеграционную ветку) | `.github/workflows/okf-gate.yml` | `install.py` (пропускает, если гейт уже гоняет другой workflow) |
| Остальной CI: валидация бандла, тесты и сборка MCP | `.github/workflows/*` | руками по `references/ci.md` |
| Деплой MCP: Deployment/Service/Ingress/токены | там, где живут манифесты команды | руками по `references/k8s.md` (пример для Helm), с подтверждением |

`install.py` идемпотентен: отсутствующее создаёт, идентичное пропускает, изменённое
локально не трогает без `--force`, `project.ts` не перезаписывает никогда, `org.ts` —
только файлом из `--org-file`. Повторный
запуск — штатный способ обновить инструменты в проекте (`--force`).

**Почему так разложено.** `AGENTS.md` читают все агенты (Codex, Cursor), Claude Code —
только `CLAUDE.md`, отсюда импорт. Блок в `AGENTS.md` короткий: правило проверяет CI для
любого автора, значит, знать его должен каждый агент. Механика нужна лишь при правке кода
или бандла, поэтому лежит в правиле по путям: Claude Code подгружает его, когда читает
файл из `paths:`, а сессии про CI, деплой или процесс за него не платят (раньше раздел
занимал до 97% `CLAUDE.md` и грузился всегда). Блок и правило — управляемые: перезапуск
переписывает их, `paths:` пересобираются из концептов. Старый блок из `CLAUDE.md`
`install.py` переносит сам; раздел про бандл, написанный руками без маркеров, — только
называет: удали его сам. Корневой `AGENTS.md` со схемой claude-memory-compiler («Personal
Knowledge Base Schema» — память, поставленная прямо в корень репозитория) он не трогает
вместе с `CLAUDE.md` и правилом: сначала перенеси память в свой каталог
(`tools/memory-compiler/`), чтобы корневой `AGENTS.md` стал инструкциями проекта, потом
перезапусти `install.py`.

**Почему свой драйвер слияния.** Каждая ветка, обновившая бандл, пишет верх `log.md`,
якорь и дату своих концептов — параллельные ветки конфликтовали там, даже когда тексты
сливались чисто: в трёх проектах 81 из 100 конфликтных мержей
были только в бандле, `log.md` — в 92, дата концепта — в половине споров внутри
концептов. `union` для `log.md` и `.okf-anchor` оставляет обе стороны; концепту он не
годится (два ключа `generated:` роняют knowledge-mcp), поэтому концепт идёт через
драйвер: если обе ветки поменяли дату, обеим ставится поздняя, дальше — обычное
трёхстороннее слияние git, спор в тексте остаётся конфликтом. На тех 100 мержах это
снимает 66, и в 64 из них бандл совпал с тем, что закоммитили люди. Драйвер живёт в
`.git/config`, который клон не переносит, — его прописывает SessionStart-хук; клон без
него сливает концепты обычным образом.

## Порядок работы

Долгие команды (`install.py`, генерация бандла, `validate_bundle.py`, `drift.py`, `npm ci`,
`docker build`) — одним блокирующим вызовом с хвостом вывода (`… 2>&1 | tail -40`), без
фонового запуска и опроса.

### 0. Разведка и решения

Прочитай `AGENTS.md` и `CLAUDE.md` проекта, `.claude/settings.json`, `.github/workflows/`,
структуру каталогов, есть ли уже `okf-bundle/`. Корневой `AGENTS.md` — схема
memory-compiler: перенос памяти — первым пунктом плана (см. «Почему так разложено»).
Определи сам:
- **базовую ветку** интеграции (`origin/develop`, если есть, иначе `origin/main`) — от
  неё Stop-хук считает «что поменяли в этой работе»;
- **имя приложения** (как оно называется в CI и деплое, префикс образа) — это `--app-slug`;
- **менеджер пакетов и форму репо** (монорепа `apps/*` или одно приложение в корне).

**Стандарт команды.** Этот скилл ничего не знает про реестр образов, кластер, секреты и
уведомления команды. Если среди доступных скиллов есть скилл, который настраивает проекты
по стандарту команды и в описании называет OKF (сетап инфраструктуры: CI/CD, деплой) —
загрузи его и возьми оттуда привязку бандла и MCP к CI, деплою и секретам, общий `org.ts`
для `--org-file` и то, что он требует показывать пользователю; план — из обоих, при
расхождении прав он. Нет такого — про деплой MCP спроси пользователя (вопрос ниже).

Спроси пользователя (одним `AskUserQuestion`), только то, что из кода не вывести:
- нужен ли **MCP для заказчика**, и если да — будет ли **клиентская** аудитория
  (ИИ-ассистент для пользователей продукта) или только заказчик;
- название продукта для заказчика, если оно не очевидно;
- MCP нужен, а стандарта команды нет — **куда его выкладывать** (реестр образов, где
  запускать, откуда берутся секреты). «Пока никуда» — годный ответ: §4 заканчивается
  образом, который собирается и отвечает локально.

Скажи, как будешь проверять результат (чек-лист в §7), до начала правок.

### 1. Бандл

Нет `okf-bundle/` — сгенерируй его **скиллом `okf`** (загрузи его и следуй ему). Для
этой обвязки важны три вещи сверх обычных правил okf:
- у каждого концепта про код — `resource:` с путём в репо (файл или каталог): только
  так `drift.py` связывает правку кода с концептом;
- если один файл описывают несколько концептов — `resource_anchors: [Symbol, ...]`
  (имена моделей/экспортов/функций, которыми концепт владеет), иначе любая правка
  файла пометит устаревшими все его концепты;
- продуктовый слой (`product/`, `policy/`, `reference/glossary`) пиши так, чтобы его
  мог читать заказчик: поведение, а не реализация — MCP отдаст именно его. Инженерное
  «почему так/грабли» — в секции «Ограничения и грабли» (заказчику она вырезается).

Бандл уже есть — прогони `validate_bundle.py` и `drift.py` после установки (§2) и
почини то, что они покажут, прежде чем ставить якорь.

### 2. Установка

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/okf-repo-setup/scripts/install.py" --repo . \
  --base-ref origin/develop --app-slug <app> --product-name "<Продукт>" \
  [--with-mcp] [--mcp-dir <dir>] [--org-file <org.ts команды>]
```

Сначала можно `--dry-run`. Прочитай отчёт: `kept` — файл отличается от шаблона
(локальные правки?) — разберись, а не жми `--force` вслепую. Предупреждения про
`AGENTS.md`/`CLAUDE.md` (схема memory-compiler, раздел без маркеров, `AGENTS.md`, который
`CLAUDE.md` раньше не подключал, — не повторяют ли они друг друга) — разбери до коммита.
Бандла ещё нет — перезапусти `install.py` после §1: `paths:` правила собираются из концептов.

Когда бандл соответствует коду — поставь якорь и закоммить его вместе с бандлом:

```bash
python3 scripts/okf/drift.py --set-anchor
```

Якорь — это коммит, состоянию кода на котором соответствует бандл. Он в файле, а не
«последний коммит, трогавший бандл»: та эвристика схлопывается после
`git pull --rebase`. Если якорь оказался не предком HEAD (ребейз), `drift.py`
берёт merge-base и предупреждает — завышает, но не прячет дрейф.

### 3. Интеграция с агентскими скиллами проекта

Если в проекте есть скиллы, которые сами правят код и коммитят (автофикс багов,
раннеры задач), добавь в них шаг между проверками и коммитом. Stop-хук их тоже поймает,
но в неинтерактивном прогоне лучше, чтобы шаг был явным. Текст шага:

```markdown
## Актуализировать бандл знаний

`python3 scripts/okf/drift.py --gate` — какие концепты `okf-bundle/` описывают код,
который ты только что поменял, и ещё не обновлены (диапазон — только твоя ветка, обычно
1–3 концепта). То же самое проверит CI на PR. Полный отчёт по ветке — `--branch`.

- **STALE** — перечитай концепт и почини разошедшееся (пороги, поля, коды ответов,
  правила) точечно, целиком не переписывай; обнови `generated.at`. Утверждение, которое
  правка сделала неверным, важнее нового текста: бандлу верят.
- **UNCOVERED / UNMATCHED** — новый файл или правка мимо якорей: концепт заводи, только
  если это отдельная сущность уровня сервиса/модели.
- Пусто — ничего не делай. Обновить нужно **каждый** концепт из списка: Stop-хук и CI
  проверяют их поимённо, пробелы и пустые строки обновлением не считаются.
- Правка не нужна по существу (рефакторинг без смены поведения) — добавь в сообщение
  коммита с кодом строку `okf: n/a — <причина>` (от 8 символов). Отказ покрывает файлы
  только этого коммита, CI его примет, а в истории останется, почему бандл не тронут.

Бандл — **отдельным коммитом** `docs(okf): ...` в той же ветке: дифф кода читается без
примеси документации. Правила авторства концептов — скилл `okf`.
```

### 4. MCP для заказчика (если нужен)

1. `install.py --with-mcp` положил сервис в `<mcp-dir>`. По умолчанию
   `apps/knowledge-mcp`, если есть `apps/`, иначе `knowledge-mcp/`.
2. **Изоляция от основного приложения.** Установщик сам:
   - добавляет каталог MCP в `exclude` корневого `tsconfig.json` (корневой
     `include: ["**/*.ts"]` иначе typecheck'ает MCP и в Docker-сборке хоста, где нет
     `express`/`@modelcontextprotocol/sdk`, падает — проверено на Next.js-монолите);
   - добавляет каталог MCP в корневой `.dockerignore`. Образ MCP при этом собирается:
     у него свой `Dockerfile.dockerignore` (BuildKit берёт его вместо корневого) —
     не удаляй его, иначе `COPY <mcp-dir>/...` не найдёт файлов;
   - `vitest.config.ts` пакета содержит `css: { postcss: {} }` — без этого vitest
     поднимается вверх и грузит `postcss.config.js` хоста (Tailwind) и падает.
   Руками (установщик предупредит): ESLint-ignores; корневой vitest/jest без явного
   `include`; `tsconfig` без `exclude`. pnpm-монорепа: каталог под `apps/*` попадёт в
   workspace — это нормально.
   После — build / lint / test основного приложения должны пройти **так же, как до
   установки** (сравни с чистым состоянием: у хоста могут быть свои старые ошибки).
3. `cd <mcp-dir> && npm ci` — `package-lock.json` приходит с шаблоном, коммить его
   вместе с сервисом (обновлять зависимости — npm 11+: npm 10 без lock-файла падает
   на дереве vitest 4). Затем заполни `src/project.ts` (и `src/org.ts`, если бандл
   называет внутренний домен или кластеры команды, а общего файла у неё нет) по
   `references/mcp-config.md` и
   добейся зелёного `npm test` и `npm run typecheck`: пока конфиг не заполнен, падает
   ровно один тест-сторож. Не ослабляй тесты ради зелёного — чини концепты или конфиг.
4. Живой прогон из `<mcp-dir>`: `npm run build && MCP_PARTNER_TOKEN=dev node dist/index.js`
   (бандл — ближайший `okf-bundle/` выше пакета, другой — через `KNOWLEDGE_BUNDLE_DIR`),
   затем `curl /health`, `tools/list` и `tools/call search_product_knowledge` с
   `Authorization: Bearer dev` — команды в README сервиса.
5. `docker build -f <mcp-dir>/Dockerfile .` из корня репо — образ должен собраться.

### 5. CI

Гейт долга ветки (`okf-gate.yml`, `drift.py --gate` на каждом PR и пуше в
интеграционную ветку) уже положил `install.py` — проверь, что `on.push.branches` —
интеграционная ветка. Остальное — по `references/ci.md`: валидация бандла на каждый пуш, тесты
MCP, сборка образа MCP по изменениям `okf-bundle/**` и `<mcp-dir>/**` и передача
собранного образа в деплой так, как это принято у команды.
Первым делом проверь ловушку `paths-ignore: '**.md'` — из-за неё пуш только бандла не
пересобирает MCP.

### 6. Деплой и токены (если MCP деплоится)

Сервису нужны: образ, один порт (`8474`), три переменные с токенами и HTTPS-хост — ни
базы, ни доступа к приложению. Для Kubernetes с Helm-чартом — `references/k8s.md` и
шаблоны `assets/k8s/`; для другого способа (compose, PaaS) возьми оттуда требования к
контейнеру и прокси. Манифесты часто живут в **другом репозитории**, из которого
деплоится прод, — покажи план и получи подтверждение перед коммитом туда. Значения
токенов не придумывай и в git не пиши. Если CI передаёт тег образа в манифесты, место
под него должно появиться там **до** первого пуша проекта. DNS-запись хоста MCP
заводит пользователь.

### 7. Проверка (обязательно, с выводом команд в отчёте)

```bash
python3 scripts/okf/validate_bundle.py okf-bundle     # 0 errors
python3 scripts/okf/graph_check.py okf-bundle         # без сирот
python3 scripts/okf/gen_index.py okf-bundle --check   # индексы свежие
python3 scripts/okf/drift.py                          # после якоря — «Дрейфа нет»
```

Stop-хук — на временном изменении, с откатом. Если бандл создан в этой же ветке,
все его концепты считаются «изменёнными в ветке» и хук молчит — для проверки
задай базу, где бандл уже есть: `export OKF_BASE_REF=HEAD` (после коммита бандла).
1. поменяй файл, на который указывает `resource:` какого-то концепта (не коммить);
2. `echo '{}' | python3 scripts/okf/stop_guard.py; echo $?` → **2** и список концептов;
3. `echo '{"session_id":"t"}' | ...` дважды → 2, затем 0 (тот же набор в той же сессии);
4. правка **другого** концепта → всё ещё 2; пустая строка в устаревшем концепте → 2;
   содержательная правка устаревшего концепта → 0;
5. `echo '{"stop_hook_active":true}' | ...` → 0; `OKF_SKIP=1` → 0;
6. закоммить временную правку кода с `okf: n/a — проверка гейта` →
   `python3 scripts/okf/drift.py --gate --branch HEAD~1` → 0 и отказ в выводе;
   `git commit --amend -m tmp` (без этой строки) → та же команда даёт 1;
7. откати временный коммит (`git reset HEAD~1`) и правки, `unset OKF_BASE_REF`.

Stop-хук и `--gate` считают концепт обработанным, только когда изменён текст **его**
файла: правка одного концепта не прикрывает другой (в первой версии любая правка
бандла снимала блокировку — это пропускало дрейф в длинных ветках), пробелы не в счёт. Метку «обновлён»
считает `drift.py` (◐ в отчёте, `refreshed` в `--json`: концепт правлен в той же
единице работы, что и его источник) и из STALE её **не убирает** — на реальном проекте 13
из 22 таких концептов оказались недообновлены, скрытие сделало бы их невидимыми.
Единица работы — смёрженный PR, текущая незапушенная ветка или, при линейной
истории без merge, серия коммитов с кодом, закрытая коммитом бандла
(`docs(okf): ...`) поверх неё; код, написанный больше чем за 12 часов до этого
